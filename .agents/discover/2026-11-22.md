## Assessment

The source deliberately defaults to noindex, including hypothetical production deployments. That is appropriate before launch. It is not yet a complete, independently tested environment-aware SEO policy, and the current robots.txt undermines discovery of noindex by compliant crawlers.

No confirmed critical issue was found within the inspected scope. The high findings below address exclusion reliability and future launch safety, not evidence that the site has already been indexed.

## High

### SEO-01 — Crawl blocking prevents discovery of noindex

Evidence:

- `public/robots.txt:1-2`: `User-agent: *` / `Disallow: /`.
- `src/pages/index.astro:16`: `noindex, nofollow`.
- `scripts/staging/headers.txt:1-2`: wildcard `X-Robots-Tag: noindex, nofollow`.

Google explicitly warns that robots.txt blocking prevents it from reading noindex; externally linked URLs can still appear in results without their content being indexed.

Choose an explicit strategy:

- Public review URLs: allow crawling so HTML and HTTP noindex can be read; retain noindex across documents and non-HTML assets, without advertising a sitemap.
- Private review URLs: access control is stronger protection for unpublished content, but requires a separately reviewed integration with deployment and browser tests.

Neither a canonical link nor an unadvertised URL is an exclusion mechanism. Do not claim zero indexing risk for public URLs or treat a client-specific 403 as authentication.

Reference: https://developers.google.com/search/docs/crawling-indexing/block-indexing

### SEO-02 — No tested indexing policy or production-host launch gate

Evidence:

- `src/pages/index.astro:16` and `scripts/staging/headers.txt:2` hardcode noindex.
- Preview, staging and production all use `scripts/staging/add-headers.mjs`.
- `.github/workflows/deploy-production.yml:111` injects the same headers into production.
- `scripts/deployment/targets.mjs:3-11` separates Worker names, not indexing eligibility.
- `scripts/staging/policy.mjs:35-55` validates HTTPS origin syntax, not an approved production hostname.
- `scripts/staging/validate-assets.mjs:55-67` validates metadata SHA, not robots/meta/canonical consistency.
- Existing unit/E2E tests do not assert indexing directives.

Current behavior is fail-closed, not an active indexing leak. Removing the unconditional noindex later without a central policy and tests would make accidental preview indexing or continued production noindex easy.

Recommendation: define preview, staging, production-prelaunch and production-launched states. Only explicit launch approval plus the approved production origin can permit indexing. A deploy flag or production build mode alone must not do so. Ensure alternate Worker/version/alias origins cannot expose indexable copies; build-time metadata cannot independently enforce request hostname behavior.

Preserve trusted deployment-side policy injection and artifact-provenance boundaries. Deployment policy should reject contradictory content rather than rely only on branch-supplied metadata.

## Medium — required for launch readiness

### SEO-03 — Production URL and discovery metadata are absent

- `astro.config.mjs:4-8` has no `site` origin.
- `src/pages/index.astro:9-20` has no canonical URL.
- No sitemap source or generated sitemap exists.
- No approved host/protocol/www redirect policy or custom 404 page exists in source.

These omissions are not defects in the intentionally unpublished environment. Before launch, configure the canonical HTTPS apex origin, self-canonical homepage and sitemap containing only indexable canonical routes. This is currently a one-page site: section fragments are not separate sitemap pages.

Verify HTTPS, www/non-www, alternate Worker URLs, query variants, clean URL variants and real 404 responses at the actual edge. Missing-page behavior is unverified, not a confirmed soft-404 bug. Artifact validation currently forbids `_redirects`; redirect handling must respect the trusted deployment boundary rather than weakening that validator.

### SEO-04 — Metadata and sharing support are incomplete

- `src/pages/index.astro:18`: generic title `Chispa con Calma — Inicio`.
- Description exists and matches visible content; Spanish document language and viewport are present.
- No Open Graph, Twitter-card metadata or social image is present.
- No JSON-LD is present.

Prepare an owner-reviewed descriptive title, sharing metadata and a licensed social image. Use factual structured data appropriate to Yolanda's business; do not invent an address, ratings, testimonials, credentials or contact details. Rich-result eligibility is not guaranteed. FAQ markup and a PWA manifest are not requirements for technically sound SEO.

### SEO-05 — Image/page-weight opportunities need performance measurement

- `public/assets/portrait.png`: 863,674 bytes, 921 × 1152 pixels.
- Both portrait elements use this same URL; that does not imply two network downloads.
- `SectionInicio.jsx:145-158` and `SectionSobreMi.jsx:52` use plain images without intrinsic width/height attributes or responsive sources.
- The below-fold portrait has no lazy-loading directive.
- Generated HTML is 135,576 bytes; emitted JavaScript totals 348,889 bytes before transfer compression.
- `src/pages/index.astro:25` hydrates the whole React home island on load.

Optimize responsive image delivery and below-fold loading without lazy-loading the likely hero/LCP image. Existing aspect-ratio containers may already limit layout shifts; missing dimensions alone do not prove a CLS failure. Measure LCP, INP and CLS before asserting performance regressions or prescribing a larger island refactor.
